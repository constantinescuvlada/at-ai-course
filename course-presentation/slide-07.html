Why it works

How Git works — the four places your code lives

Step 1 was a single git clone, but Git keeps coming back: in Step 7 you'll tune a .gitignore, and every file you write from Module 4 onward is worth saving. Git's whole model is four places a change can sit, and one command to move it to the next:

Working folderthe files you edit
→
Staging areagit add
→
Local historygit commit
→
GitHub / Bitbucketgit push
  • Working folder — the ai-bot-learn/ directory on your disk. Editing a file touches nothing else.
  • Staging area — a shortlist of the changes you want in your next save. git add puts them on it.
  • Local history — the chain of commits kept in the hidden .git/ folder. A commit is one snapshot plus a message saying what changed.
  • Remote — the copy living on a hosting site — GitHub for this course, Bitbucket at many companies. git push sends your commits up, git pull brings other people's down.
git status              # what changed?
git add .               # stage everything
git commit -m "Add search endpoint"
git push                # up to the remote

git log --oneline       # past commits
git diff                # unstaged changes
Nothing is safe until you commit, and nothing is shared until you push. That is also why .gitignore (Step 7) matters — it keeps venv/ and postgres/ off the staging list, so a commit stays small and readable. This course never asks you to push, but committing at the end of each module leaves you a working point to come back to when something breaks.
